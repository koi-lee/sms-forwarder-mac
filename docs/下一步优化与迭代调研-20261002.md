## 结论

这个项目的窄价值是：为已拥有兼容短信转发设备的 Mac 用户，提供免手工串口命令的设备识别提示、短信正文解析、短信卡片和设备推送日志查看。它不是短信转发服务器；收短信、联网和 Bark 推送由设备固件负责。当前最值得优先改善的是让用户看懂“设备收到了，但固件没有转发”的失败状态及事件时间，而不是加更多串口功能。

Build 6 是仓库当前最新预览版，GitHub `Latest` 指向 Build 5。2026-10-03 核对 GitHub 官方文档后确认，预览版不能被设置为 `Latest`；因此保留正式版 `Latest` 语义，通过 README 和官网的 Build 6 直达入口标清“最新预览版”。本报告未修改 GitHub Release 元数据或官网。

**本轮推进结果**：已补设备 PDU 错误卡片状态、短信与助手观察时间来源标签、首页职责提示，并修复 macOS Bash 3.2 下构建脚本的空数组兼容问题。GitHub 的 `Latest` 不能指向预览版，保留当前 Release 标记和预览状态。合成回归 190 项通过，本地构建成功；界面预览、真机短信/推送/拔插、Apple 公证、DMG 和公开发布均未完成，详见[项目状态与交接](项目状态与交接.md)。

- **自检基线**：调研时 `python3 Tests/run-decoder-tests.py` 通过 184 项，覆盖 GSM 7-bit 默认字母表、UCS-2、扩展字符、分段头和损坏输入。2026-10-03 状态分类新增 6 项检查后共 190 项通过。代码静态核对确认助手不自动发送 AT 指令、不独立向 Bark 推送；用户选择保存日志后才写入本地文件，日志可含短信内容、号码、IP/MAC 和 PDU。界面缓冲有上限，保存日志有 100 MiB 单文件上限，但没有做高吞吐下 CPU/内存实测。相关说明见[隐私与来源](隐私与来源.md)、[快速上手](快速上手.md)和[使用与排查](使用与排查.md)。

## 首次使用路径与问题

核心路径是：安装 Build 6 → 确保设备已供电、配网且配置推送 → 用 USB 连接 → 选设备串口并按说明设为 115200、8-N-1 → 点击“连接并监听” → 从手机向设备内 SIM 发送一条新短信 → 对照 Mac 卡片、设备日志与手机 Bark。已经在连接前到达的短信不会由助手补读；退出应用后短信卡片也不持久保存。设备正常转发不依赖 Mac 助手一直运行。

1. **设备推送失败可能在卡片上显示为等待——已实现，待真机验收。** 2026-10-02 的设备复测中，验证码到达设备、Mac 可解析正文，但设备紧接着输出“PDU解析失败”，用户确认 Bark 未收到。2026-10-03 已让短信卡片识别该设备状态并保留原始行；同一条记录同时出现设备 PDU 错误和推送结果时，显示“结果需核对”。合成状态回归已覆盖，但没有真实串口复验。该显示不能修复设备固件或替设备重试。
2. **时间字段容易让人把投递延迟归错层——来源已标注。** 短信卡片显示短信时间（PDU 原值，时区未换算），以及 Mac 从串口读取到完整 PDU 行时的助手观察时间。后者不是基带接收的精确时刻。源码只读取 PDU SCTS 前六个日期/时间字段，未应用第七个时区字段（[SerialAssistantApp.swift](../Sources/SerialAssistantApp.swift#L212-L214)）。现有信息仍不足以单独判断运营商、设备队列、固件推送或 Bark 哪一层造成延迟；HTTP 200 也不能证明手机已收到。
3. **设备与 Mac 助手的分工可能被误解——主窗口已补充。** 多次真实对话中用户询问 App 关闭后是否能转发。主窗口现在说明“短信接收与 Bark 推送由设备完成；Mac 助手通过 USB 显示日志”。Build 6 源码没有在真机上运行此界面，故措辞和布局仍待实际体验。
4. **设备断开后的状态恢复值得实测。** 当前读取回调对 `read()` 返回 0 或负数直接返回，不更新连接状态（[SerialAssistantApp.swift](../Sources/SerialAssistantApp.swift#L398-L409)）。这意味着拔掉设备后界面可能仍显示“已连接”；这是代码路径风险，尚未在实际拔插中复现。先验证状态，再决定是否加自动重连。
5. **热点不见未必是故障。** 用户遇到过找不到 `ESP32-AP` 和 `SMS-Forwarder-AP` 热点。卖家说明书写明：设备成功连上家中 Wi-Fi 后配网热点可能关闭，且要求 2.4 GHz。新的本地配网说明已记下两种名称与恢复广播条件；说明书 PDF 因含家庭路由器信息未入库。
6. **可访问性与日志清除语义未验收。** 主窗口最低尺寸为 900×780，打赏窗口为 720×560；本轮未做 VoiceOver、仅键盘操作、大字号或小屏检查。另，“清空”按钮只清空窗口缓冲和字节计数，已选中的日志文件仍保持打开并继续追加（`clearLog()`；[SerialAssistantApp.swift](../Sources/SerialAssistantApp.swift#L478-L480)），界面没有说明这一点。日志文件可能含敏感短信数据，应在小屏/辅助功能走查时顺便确认用户能看懂“清空窗口”和“删除已保存文件”的区别。

## 建议的前三项验收

1. **下载入口验收**：新用户从仓库 README 和官网产品页均能明确选中 `v0.1.0-preview.6`，不需要猜哪个 Release 更新；安装教程、Release 文件名和关于窗口版本一致。若保留 GitHub `Latest` 的稳定版语义，则在入口直接标出“最新预览版 Build 6”。
2. **设备错误验收**：用合成串口文本触发解析失败，短信卡片从等待状态变为明确设备错误；成功、失败、尚无结果三种状态不混淆，且不把错误归到相邻短信。
3. **首次理解与时间验收**：不发真实短信，给未参与开发的人看主窗口和一段合成时间线，确认其能说出谁负责 Bark、Mac 是否必须常开、哪一个时间是短信中心字段、哪一个是助手观察日志时间。若时间来源无法从当前串口数据可靠确定，就暂缓 UI 耗时结论，只保留来源明确的时间字段。
